# TS001 共享执行与审核合同（占位）

> 本文件是 `TS001-IMPL` 与 `TS001-VAL` 共同引用的需求、边界和测试合同占位。它不是新的 canonical 对象，也不是实现授权。

## 目的

为 Codex → Pi-开发 → Pi-审核 的第一组协作切片提供同一份可复算的范围、非目标、验收和失败语义。两个 TaskSlice 必须引用本文件的同一 revision 与 SHA-256。

## 已确认的协作结构

| TaskSlice | 主体 | 责任 | 允许的结果 |
|---|---|---|---|
| `TS001-IMPL` | Pi-开发 Agent | 按冻结合同实现最小合同与测试基线 | 候选版本、执行证据和开发 `ResultBundle` |
| `TS001-VAL` | Pi-审核 Agent | 独立复算、运行测试、检查偏差与绕过 | 审核证据和审核 `ResultBundle` |

`TS001-IMPL` 与 `TS001-VAL` 是两个独立 TaskSlice；共享前缀只是命名分组，不存在父对象 `TS-001`。

## 最小合同范围

- 受测操作合同：`TaskSlice`、`HandoffBundle`、`ResultBundle`。
- `ExperimentSpec` 只提供最小只读 Schema：`spec_id`、`version`、`status`、精确数据/fixture 引用（含 `data_class`）、验收指针和 provenance；本切片不实现其 mutation。
- `ExperimentSpec@v1` 的首次建立采用带 G-002、来源、版本、hash 和批准指针的人工 bootstrap；后续切片只读引用。
- `TaskSlice` 的语义内容变化创建新 revision；生命周期状态变化通过 transaction + Event 表达。
- `HandoffBundle` 与 `ResultBundle` 是不可变操作记录，不属于八类研究 canonical 对象；被拒绝的提交也必须保留。

## TS-002 预留边界

`TS-002` 只负责协作闭环、allowlist、候选版本冻结、hash 复算、幂等提交和 Harness 登记。Run 侧完整记录、Evidence 和 Claim 另列后续切片，不在本合同中提前实现。

## TS-001 交付与入库计划

TS-001 的交付采用“候选先留在 workspace、审核后再申请入库”的两阶段路径：

1. `TS001-IMPL` 只能把 Schema、纯数据 fixture、测试载体和执行证据写入自己的 attempt workspace，并通过受控通道提交 `ResultBundle`；不得直接写 `02_架构与合同/schemas/`、`04_测试与验收/fixtures/` 或其他 canonical/受治理路径。
2. `TS001-VAL` 独立复算候选。`CONFORMANT` 只表示按冻结合同未发现工程偏差，不构成入库批准。
3. 只有在 VAL ResultBundle 已提交、候选 SHA 已由协调方复算并冻结，且用户对本次候选入库作出明确批准后，协调方才可执行一次 pre-Harness canonical bootstrap：逐文件复算 SHA、核对目标与引用、写入允许的目标位置，并在唯一 LOG 与交接记录中留痕。
4. 入库目标暂定为 `02_架构与合同/schemas/`（四份 Schema）与 `04_测试与验收/fixtures/FX-001/`（登记后的纯数据 fixture）。目标清单若发生变化，必须先修订 TaskSlice 的 `promotion_plan` 并重新走相应 Gate。
5. 入库不是自动晋升，也不能由 `CONFORMANT`、工具退出码或包状态推断。入库后发现 canonical 文件缺陷，按 G-014 处置；fixture 内容变化按 G-011 处置；原始候选和历史记录不得覆盖或静默删除。

因此，`promotion_plan` 是两个 TaskSlice 都必须填写的字段：IMPL 描述候选交付与待批准入库，VAL 明确“不负责入库”。

## 任务包与审核包模板合同

### 共同骨架

Implementation Task Package 与 Validation Review Package 都是对应 HandoffBundle 的载荷/derived view，不是新的 canonical 对象。两者共同使用：

1. 范围；
2. 入口与指针；
3. 产出清单；
4. 门禁。

包内每个字段必须追溯到 TaskSlice 字段，或追溯到 exact inputs 引用的冻结合同文件。包与冻结合同冲突时以合同为准。

### 两类扩展

- Implementation Task Package：权限与 allowlist、validation commands、停止条件、retry、rollback、执行报告格式；
- Validation Review Package：独立性、前置条件、盲审先行顺序、负向测试、只读范围、判定词表和审核报告格式。

任务包/审核包正文作为对应 HandoffBundle 的载荷一次渲染并固定一个 SHA；渲染错误创建新包版本，不修改已生成的不可变记录。模板文件位于 `templates/`，模板变更必须经过 G-010；已生成包不因模板更新而改变。

### VAL 判定词表

`TS001-VAL` 的 ResultBundle `verdict` 只能使用以下四个工程域词：

| Verdict | 含义 | 明确不等于 |
|---|---|---|
| `CONFORMANT` | 按冻结 revision 与候选 SHA 完成盲审和交叉核对，未发现偏差 | `approved`、用户人类验收、科学支持 |
| `DEVIATIONS_FOUND` | 发现偏差、绕过或缺口，并附清单与复现指针 | 自动修复、批准拒绝科学主张 |
| `INCOMPLETE` | 审核无法完成，例如候选漂移、SHA 不符或输入缺失 | 通过 |
| `OUT_OF_SCOPE` | 发现超出本 TaskSlice 范围的事项，转协调方或用户另行处置 | 本切片的失败判定或批准 |

该词表与 `proposed`、`accepted`、`tested`、`human-accepted` 等状态词隔离；`CONFORMANT` 不得被渲染为 PASS 或 approved。

## 共同约束

- 两个 TaskSlice 引用本文件的同一 SHA；本文件变更必须创建新 revision，并使双方重新通过 G-003。
- `TS001-VAL` 的审核合同在候选版本出现前冻结；候选 path + SHA 通过 HandoffBundle 到达。
- `TS001-VAL` 的前置条件是 `TS001-IMPL` 已 accepted 且候选 SHA 已冻结；否则不得进入 `running`。
- VAL 只读与本 TaskSlice 相关的冻结合同、验收文件、候选 HandoffBundle/ResultBundle 和候选文件；只写自己的审核 workspace；不得写 IMPL workspace、canonical state 或 `00_入口/00_当前.md`。不得以“读全库”作为默认权限。
- 审核分为盲审和交叉核对两段：盲审先独立复算，之后才核对开发 `ResultBundle`/报告；两段必须分开记录。
- Pi worker 不得使用真实医疗数据、网络下载或未登记数据；不得直接写 canonical state。

## TS-001 沙箱与验证环境

### 写入边界

“不写生产库”的精确含义是**库根只读 + 白名单写入面**，不是禁止写入库内 workspace：

- 可写：本 TaskSlice 自己的 `03_实现/workspaces/<task_slice_id>/<attempt_id>/`，以及受控的 `ResultBundle` 提交通道；
- 只读：canonical 区、`00_入口/`、`07_运行记录/`、`templates/`、`.obsidian/`、对方 workspace 和所有未列入 allowlist 的路径；
- Pi 不得直接写 canonical state、Research Event、Manifest 或 `00_入口/00_当前.md`；保留的操作记录由协调方/Harness 通过受控通道登记；
- VAL 不得写 IMPL workspace，也不得复用 IMPL 的缓存、scratch 或中间产物。

### 候选 SHA 的 pre-Harness 规则

TS-001 尚无 Harness 时，候选冻结按以下顺序成立：

1. IMPL 在 `ResultBundle` 中提交候选 path + SHA，并明确标记 `pre_harness_unverified`；
2. Codex 作为协调方逐项复算候选 SHA，并在交接记录中保存复算结果；
3. HandoffBundle 将 path + 协调方复算 SHA 送达 VAL；
4. VAL 每次读取候选文件前重新复验 SHA；任一不一致视为候选漂移，`fail_closed`，退回新 attempt；
5. TS-002 Harness 上线后，候选 hash 复算职责移交 Harness。

协调方复算只是保管链校验，不等同于 Harness 权威写入，也不等同于用户验收。

### 网络与运行时边界

- 合同层保证：allowlist 不包含网络工具、下载工具或凭据读取工具；违反即 `fail_closed` 并追加拒绝记录；
- 环境层保证：由用户在 Pi 侧配置无网络或离线、无凭据的执行环境；P0 不要求实现技术性网络沙箱；
- 两层必须分别记录，不能把环境尽力隔离写成 Harness 已强制执行。

IMPL 与 VAL 使用同一沙箱策略，但必须是独立会话、独立 workspace 和独立缓存。VAL 从冻结候选 SHA 重新开始验证，不继承 IMPL 的运行状态。

### 验证命令与记录

- `validation_commands` 是运行时无关的合同，基于标准 JSON Schema 和纯数据 fixture，不反推 Q-007 的生产实现语言或状态后端；
- 任务包可以推荐固定版本的验证工具链；实际运行时、工具版本和环境信息必须进入 ResultBundle；
- 每条命令至少记录：命令、运行时及版本、输入 SHA、输出/日志 SHA、退出码、起止时间；
- TS-001 的负向测试只操作 schema/fixture 数据层，不触碰真实 canonical 路径；未来 filesystem gate 验证必须在副本库中并显式写入 allowlist。

## 操作记录物理位置

HandoffBundle 与 ResultBundle 的保留路径统一为：

```text
06_任务与交接/records/<task_slice_id>/<attempt_id>/
```
