# 实体与版本合同

## 核心身份

| 类型 | 前缀 | 作用 |
|---|---|---|
| Hypothesis | H | 假设 |
| Protocol | P | 协议与判定规则 |
| ExperimentSpec | E | 准备执行什么 |
| TaskSlice | TS | 最小执行任务 |
| Run | R | 一次实际执行 |
| Artifact | A | 内容寻址产物 |
| RawUnit | RAW | 原始证据单元 |
| EvidenceCard | EVID | 整理后的证据 |
| EvidenceSnapshot | ES | 某次报告考虑的证据集合 |
| Claim | C | 原子结论 |
| Decision | D | 人工/治理裁决 |
| Event | EV | 状态变化 |
| Transaction | TX | 原子提交 |
| Handoff | HO | 责任交接 |
| ResultBundle | RB | worker 提交的不可变结果包；不是研究 canonical 对象 |

## 四种标识不得混用

- entity_id：跨版本稳定身份，如 E017。
- versioned_ref：精确版本，如 E017@v4。
- content_hash：某次字节内容 SHA-256。
- path：当前物理位置，可迁移但不定义语义身份。

## 版本规则

1. semantic change 创建新版本。
2. presentation-only change 必须由工具或人工明确分类。
3. 一旦被 Run 引用，ExperimentSpec revision 永久冻结。
4. terminal RunManifest、Event、Decision、Handoff attempt 不覆盖。
5. 修订记录 supersedes、reason、changed_fields 和 impacted_entities。
6. 上游 revision 自动使下游进入 stale/needs_review，不自动科学否定。
7. 文件移动通过 ID 与 hash 解析，不留下迁移残桩。

## 五层存储

| 层 | 内容 | 规则 |
|---|---|---|
| canonical state | definitions、approved pointers | revision/transaction |
| immutable records | Run、Event、Decision、HandoffBundle、ResultBundle | append-only；不得覆盖；被拒绝的提交也保留 |
| artifacts | outputs、logs、metrics | content hash |
| workspace | 临时 checkout、scratch | 可丢弃 |
| derived index | SQLite、索引、materialized view | 可删重建 |

## TS-001 / TS-002 协作分层

- `TS001-IMPL` 与 `TS001-VAL` 是两个独立的 TaskSlice；共享前缀只是命名分组，不物化父对象 `TS-001`。
- 两个 TaskSlice 必须引用同一份共享需求与测试合同及其相同 SHA；共享合同变更创建新 revision，并要求双方重新通过 G-003。
- `TS001-IMPL` 的 attempt 产生候选版本和 `ResultBundle`；`TS001-VAL` 只读取冻结候选、在自己的 workspace 中验证并提交自己的 `ResultBundle`。
- TaskSlice 的语义内容变化使用 revision；`ready`、`running`、`submitted`、`accepted` 等状态变化使用 transaction + Event，不把状态跃迁误当作内容 revision。
- `ResultBundle` 是 worker 的提交/申请记录；Harness 复算后的接受或拒绝结果才是权威事实。两者均不得放在可丢弃 workspace 中作为唯一留存。
- HandoffBundle 与 ResultBundle 的保留路径为 `06_任务与交接/records/<task_slice_id>/<attempt_id>/`；`handoffs/` 只保留历史索引/指针，不复制正文。
