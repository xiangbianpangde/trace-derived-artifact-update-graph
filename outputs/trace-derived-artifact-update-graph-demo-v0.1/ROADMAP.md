> **项目代号**：DAUG (Trace-Derived Artifact Update Graph)  
> **当前阶段**：Phase 0 (MVP 方案与核心验证阶段)  
> **文档版本**：v1.0 (演进基线)  
> **更新日期**：2026-09-28  

---

## 1. 项目愿景与核心使命

### 1.1 核心痛点与行业背景
在长周期、复杂的现代软件工程和知识密集型系统中，单一代码或配置的变动极易引发跨领域制品的连锁失效（包括 API 契约、系统设计文档、测试用例、部署脚本和运行手册）。
- **静态分析的局限**：AST 与依赖图无法跨越代码与非代码制品（Markdown、配置、测试计划）之间的语义鸿沟。
- **纯语义检索 (RAG) 的短板**：检索到的往往是“主题相似”的文档，而无法判断“本次接口变更究竟推翻了该文档中的哪一个具体陈述”。
- **大模型注意力漂移**：超长程 Agent 在上下文窗口压缩、长期执行或多 Agent 协作时，缺乏持续的外部拓扑记忆，极易遗忘隐式更新义务。

### 1.2 DAUG 核心机制创新
DAUG 提出了一种全新的**行为感知与因果验证闭环**：
1. **轨迹即观测**：将 Agent 与人类开发者在真实环境中的工具调用轨迹（`read`, `search`, `edit`, `write`, `test`）作为系统更新关系的动态观测信号。
2. **多源证据融合构图**：融合 Git 协同历史、静态代码引用、显式文本路径、语义向量与工具行为轨迹，构建有方向、带变更类型（`ChangeType`）的加权拓扑图，负责**高召回率候选定位**。
3. **独立陈旧性判定 (Staleness Verification)**：候选召回不等于更新许可。由专门的验证器比对代码差异与目标制品的具体陈述（Claim Span），输出可溯源的四态结论（`VALID` / `STALE` / `UNCERTAIN` / `NOT_APPLICABLE`）。
4. **内容寻址与写回安全网**：结合内容哈希校验（CAS）防止并发写穿，采用分级写回策略，严禁推荐行为自强化污染图权重。

## 2. 系统核心架构与演进拓扑

系统遵循严格的**分层解耦与单向数据流**原则：

```
[Agent 工具事件流 / Git 历史 / 静态引用 / 语义向量]
                     │
                     ▼
          ┌─────────────────────┐
          │  01. 证据账本与注册   │  <-- SQLite WAL, Content-Addressed Storage
          └──────────┬──────────┘
                     │
                     ▼
          ┌─────────────────────┐
          │  02. 动态制品更新图   │  <-- 变更类型 (ChangeType) 驱动 Top-K 召回
          └──────────┬──────────┘
                     │ (候选集合)
                     ▼
          ┌─────────────────────┐
          │  03. 陈旧性独立验证器 │  <-- 比对代码 Diff 与 Claim，输出 4-State 判定
          └──────────┬──────────┘
                     │ (STALE + 证据)
                     ▼
          ┌─────────────────────┐
          │  04. 补丁提案与写回网 │  <-- CAS 校验、风险分级、人在回路 (L1/L2/L3)
          └─────────────────────┘
```

### Phase 0: 概念验证与只读 MVP 闭环（Week 1 - Week 4，当前阶段）

- **实施周期**：4 周（1 人主导实施 + 1 人兼职评审）
- **核心边界**：**只读**、**只提补丁**、**绝不自动修改源码/Git**。

### Phase 1: 科学基准与方法学突破（Month 2 - Month 3）

- **阶段目标**：建立跨仓库、跨语言的大规模严谨评测基准，论证工具轨迹相比传统静态与时序基线的独立信息增益，产出顶会学术成果。
- **实施周期**：2 ~ 3 个月

#### 关键演化模块：
1. **构建学术级公开基准 (DAUG-Bench)**：
   - 筛选 10 个以上活跃开源仓库（包含 TypeScript、Python、Go、Rust）。
   - 构建按时间切分（Temporal Split）的真实回放集，严格隔离未来信息（No Future Data Leakage）。
   - 制定四类标签标注手册，引入双盲标注与争议仲裁流程。
2. **强基线对比与严谨消融**：
   - 对比基线包括：时序关联规则（Temporal Co-change）、高级排序学习（RankLib / LightGBM-Rank）、语义混合检索（Dense Retrieval / BM25）、静态调用图扩展（Expanded Static Call Graph）。
   - 证明增益独立于大模型本身能力，且不能由代码路径或文件名前缀泄露所解释。
3. **陈旧验证粒度下沉 (Claim-level Anchoring)**：
   - 从文件级推进到段落/陈述级（Claim Span），引入 AST 符号锚点、Markdown Section 哈希映射。
   - 提升验证器的可解释性，提供精准到行级的反例依据。
4. **学术论文与开源规划**：
   - 产出高水平学术论文预印本（拟投往 ICSE / FSE / ASE / ACL 等软件工程或 AI 顶会）。
   - 开源基准测试套件、轨迹生成器（Fixture Generator）与协议规范。

**阶段准出里程碑 (Gate M1)**：
- [ ] 在 10 个基准仓库中，DAUG 相比最强非轨迹基线的 Hit@5 提升 ≥ 15%，MRR 提升 ≥ 10%。
- [ ] 完成自强化衰减实验并证明推荐循环不发生系统崩溃。
- [ ] 论文完整初稿及可复现实验代码包冻结。

### Phase 2: 生产环境辅助式部署（Month 3 - Month 6）

- **阶段目标**：将 DAUG 深度集成进日常 Agent 宿主（Pi Harness、Codex、VS Code、Cursor 等），实现 L1 (推荐检查) 和 L2 (补丁草案) 的日常人机协作。
- **实施周期**：3 ~ 6 个月

#### 关键演化模块：
1. **宿主集成与开发者体验 (DevX)**：
   - 打造轻量级 CLI 工具（`daug_check` / `daug_patch`）与后台 Daemon 守护进程。
   - 实现 IDE / 编辑器侧边栏实时通知：当代码修改保存时，后台秒级提示潜在受影响的文档与配置。
2. **三级写回策略与人在回路 (Human-in-the-Loop)**：
   - **Level 1 (Recommend)**：仅在侧边栏显示“相关制品待审查”提示及变更原因。
   - **Level 2 (Propose)**：生成 CAS 绑定的最小补丁（Unified Diff），由开发者一键确认应用。
   - **Level 3 (Sandbox Apply)**：仅针对低风险、可完全重新生成的衍生制品（R0 级，如 API 目录索引、静态类型存根），在隔离沙箱通过测试后允许自动写回。
3. **受保护制品绝对安全隔离**：
   - 权限策略、法律合规文本、生产配置、核心科研结论等资产划入 R3/R4 风险级，系统仅允许输出风险备忘，严禁任何自动写回代码路径。
4. **真实团队 A/B 部署与成效量化**：
   - 追踪指标：漏改率（Stale Artifact Escape Rate）、任务排查时长、补丁采纳率、开发者满意度。

**阶段准出里程碑 (Gate M2)**：
- [ ] 团队内至少 3 个核心项目稳定运行 30 天无阻断性事故。
- [ ] 补丁采纳率（Human Acceptance Rate）≥ 70%。
- [ ] 发生哈希漂移（并发修改）时 100% 触发 CAS 保护熔断，未发生任何非预期覆盖。

### Phase 3: 多 Agent 联邦与自主协同维护（Month 6 - Month 12+）

- **阶段目标**：支持跨仓库、多 Agent 并发协作场景下的更新拓扑融合、动态遗忘与终身受控自愈。
- **实施周期**：6 ~ 12 个月以上

#### 关键演化模块：
1. **多 Agent 轨迹联邦与归因**：
   - 支持多 Agent 同时工作时的事件流交织拆解与权限追踪。
   - 建立任务级的图更新隔离区，合并前进行语义冲突与拓扑冲突检测。
2. **时序图动力学与概念漂移（Temporal Dynamics & Forgetting）**：
   - 引入边权半衰期与动态遗忘算法：长期未被触碰或被重构代码隔断的旧更新边自动衰减淘汰，防止图规模无限膨胀。
   - 识别模式漂移（如系统架构大重组后旧轨迹权重的批量失效与软重置）。
3. **跨仓库/微服务架构的拓扑迁移**：
   - 针对分布式微服务群、Monorepo 及跨仓库依赖，建立跨制品边界的全局更新图。
   - 支持轻量级图嵌入（Graph Embedding）在相似新项目中的冷启动迁移。
4. **全生命周期可信审计与溯源证据链**：
   - 将更新决策链（Event -> Graph Score -> Verification Evidence -> Patch -> Approval）全面持久化为不可篡改的审计账本。
   - 支持对任意历史自动变更进行全链路因果回溯与一键原子回滚。

**阶段准出里程碑 (Gate M3)**：
- [ ] 支持 5+ 个异构 Agent 在 Monorepo 中的高并发无冲突协同。
- [ ] 动态遗忘机制使图存储与检索延迟保持在 O(1) 稳定时间常数。
- [ ] 形成企业级高可靠 Agent 外部记忆与协同维护基础设施规范。

## 5. 风险控制与熔断红线

在全生命周期的任何阶段，必须严格守住以下**四条不可逾越的工程红线**：

1. **绝对禁止未经授权的真实环境写回**：
   任何自动化动作必须受到细粒度策略矩阵（Write Policy Matrix）约束，默认只产生补丁提案（Proposal），未经明确授权或在受保护区域（R3/R4）绝不触发物理写盘。
2. **严防系统推荐的“自我强化陷阱”**：
   自发访问（Organic Trace）与推荐后访问（Assisted Trace）在事件账本中必须物理分流。推荐带来的后续点击绝不允许反向无门槛推高边权，必须经过衰减折扣与双盲校验。
3. **CAS 内容哈希校验熔断**：
   补丁提案生成时刻与应用时刻必须做目标制品 SHA-256 强校验。一旦产生一比特的并发漂移，立即熔断更新并强制退回重新评估。
4. **不确定性（UNCERTAIN）必须立即停机交接**：
   验证器在上下文证据不足、模型信心不足或解析歧义时，必须显式输出 `UNCERTAIN` 并停止自动化流程，坚决杜绝“幻觉式强行修改”。
